## 背景

大学の文化祭で出店するときは、アプリを作り慣れた人がレジを作るか、現金と紙で管理していた。一方、既存の POS アプリは登録や契約が必要で、一日だけ使うには大げさだった（[README](../README.md)）。

開発のきっかけは、一日だけのためにレジを用意したり、アカウントを作ったりしたくないことだった。MVP ではそれを解決する（[0013](decisions/0013-main-and-sub-targets.md)）。

## 目的

| 項目 | 内容 |
|---|---|
| 届ける価値 | 登録も契約もせず、一日だけ使うレジをすぐに用意できる |
| 迷ったときに優先すること | 手軽さ。便利でも手順が増えるなら足さない |
| うまくいった状態 | 実際のイベントの場で使われること |

## 届けたい人

文化祭などで一日だけレジが欲しい人。役割の違う2種類の人がいて、MVP ではメインターゲットを優先する（[0013](decisions/0013-main-and-sub-targets.md)）。

- **メインターゲット：用意する人**。出店の準備でレジを選んで用意し、終了後の集計も受け持つ。登録や契約をせず、直前に決まった商品をすぐ登録してレジを用意したい
- **サブターゲット：接客する人**。当日、その場で使い方を聞いて会計する。使い方を覚えなくても会計でき、間違えたら自分で直したい
  - 文化祭のレジ係は、使い方をちゃんと教わる機会がないことが多い。そのため、直感的に使えることが大事になる

文化祭では、2つの役割を同じ人が受け持つことも多い。単発のレジを欲しがっているのは用意する人だが、レジとしての価値を受け取るのは接客する人である（[0010](decisions/0010-user-journey-in-docs-research.md)）。

## 利用場面

ユーザージャーニーマップ（開発者自身の出店経験とヒアリング）で分かったこと。

- 大学の文化祭の模擬店。研究室のメンバー5人ほどで出店する。店舗ごとに別のレジを使う
- レジはノート PC 1台を屋台に置き、時間帯ごとの当番がみんなで使う。スマホアプリは合わない
- 商品は1店舗あたり10種類ほど。商品の構成と価格は直前に決まる
- 「会計から一律50円引き」の割引券を研究室で用意して配った
- PayPay で払いたいお客さんからは店員個人が送金を受け、あとでその分の現金をレジに入れた。記録では支払方法を分けず、それで困らなかった
- 入力の間違いが全体の2割ほど起きた。間違いにはほとんど会計の直後に気づいた。直すなら「直前の会計を取り消して打ち直す」のが一番楽
- 混む時間帯は特になかった。レジはインターネットを使わず、当日の朝の準備はいらなかった
- 終了後、現金とレジの記録を手作業で照らし合わせた（一致した。時間はそれほどかからなかった）。売上の CSV を代表に送れば、用意する人の役目は終わった
- 学祭実行委員への報告の項目は、売上の合計と経費・利益

## 困りごとと、Dayresi での対応

| 困りごと | 対応 |
|---|---|
| 合うレジがないので、作れる人が自分で作るしかない（全体で一番面倒だった） | Dayresi の中心となる価値。登録不要、PC 1台、自動計算で対応する |
| 商品の構成と価格が直前に決まるので、商品の登録も直前になって面倒 | 登録するのは商品名と価格だけにする。別の端末で登録し、設定ファイルで持ち込むこともできる |
| 入力の間違いが2割ほど起き、直せるのはレジを作った人だけ | 接客する人も、履歴から確定後の会計を取り消せる。打ち直しは手で入れ直す（[0012](decisions/0012-keep-void-as-is.md)） |
| 「割引」ボタンを押し忘れる | 割引機能は作らない。価格をマイナスにもでき、「割引 −50円」を商品として登録して代用する（[0011](decisions/0011-allow-negative-price.md)）。押し忘れそのものは防げない |

## 必ず守ること

SPEC.md の「必ず守ること」。MVP でも、そのあとでも、これに反するものは作らない。

- アカウント登録をしない
- 一日、あるいは数日の単発利用が目的（MVP は一日）
- DB などでデータを管理しない
- 開発者が常に管理しなければならないものにしない

## MVP でやること

ジャーニーマップのフェーズごとにまとめる。細かい仕様は SPEC.md を見る。

### レジの準備

- 商品として登録するのは、商品名と価格（税込）だけ。在庫管理はしない
- 価格はマイナスにもできる。割引券の代わりに使う（[0011](decisions/0011-allow-negative-price.md)）
- 別の端末で商品を登録して設定ファイルに書き出し、レジの PC で読み込める。設定ファイルに売上データは入れない

### 当日の会計

- 商品ボタンをクリックしてカートに入れる。操作はマウスで行う
- カートでは数量を増やしたり減らしたりできる。0 にするとカートから消える。消すときは一括のクリアだけで、行ごとの削除はしない（[0016](decisions/0016-cart-clear-only.md)）
- 合計が0円未満になる会計は確定できない（[0011](decisions/0011-allow-negative-price.md)）
- 支払方法は分けない。キャッシュレスで受け取った分も、現金と同じように記録する（[0018](decisions/0018-cash-only-payment.md)）
- お預かり金額を画面のボタンで入力すると、おつりを表示する。入力しないまま確定すると「ちょうど」として扱う
- 確定した会計は取り消せる。取り消した会計は履歴に「取消済」として残し、集計には入れない（[0012](decisions/0012-keep-void-as-is.md)）

### 終了・集計、報告

- 売上合計と会計件数、商品ごとの数量・金額を出す。「割引 −50円」の件数と金額も、商品ごとの集計に出る
- 売上明細を CSV で保存する。Excel で文字化けしないよう、BOM 付き UTF-8 にする

### データと動作環境

- データはその PC のブラウザ（localStorage）だけに保存し、サーバーには送らない。「全データ消去」ボタンを用意する
- 一度ページを開けば、通信がなくても動く（PWA）
- ボタンは大きく、シンプルにする。PC のダークモードに合わせる。言語は日本語
- Vite＋React＋TypeScript で作る。公開物は静的ファイルだけにし、GitHub Pages で公開する

## MVP でやらないこと

### 理由を ADR に残したもの

| やらないこと | 理由 | ADR |
|---|---|---|
| 割引機能 | 集客に割引券を使う出店はありそうだが、コアバリューからは遠い。マイナスの価格で代用できる。MVP のあとで考えたい | [0011](decisions/0011-allow-negative-price.md) |
| 取り消した会計をカートに戻して打ち直す | MVP では、取り消して打ち直せればよい | [0012](decisions/0012-keep-void-as-is.md) |
| 商品を残したまま、売上だけを消す | MVP をメインターゲットに絞るため | [0015](decisions/0015-no-sales-only-reset.md) |
| カートの行ごとの削除 | MVP をメインターゲットに絞るため | [0016](decisions/0016-cart-clear-only.md) |
| 経費の記録・利益の計算 | MVP をメインターゲットに絞るため | [0017](decisions/0017-no-expense-profit.md) |
| 支払方法の区別 | MVP をメインターゲットに絞るため | [0018](decisions/0018-cash-only-payment.md) |
| 同人誌即売会などでの利用 | ユーザージャーニーマップでターゲットに含めていない | [0019](decisions/0019-school-festival-only.md) |

### SPEC にだけ書いてあるもの

SPEC.md の「MVP で扱わないもの」にあるが、理由は記録していない。

- 複数端末での同時会計・売上の合算
- 在庫管理、セット価格・オプション
- レシート・領収書、整理番号の発行
- レジ締め（釣銭準備金と実際の現金の照合）
- 時間帯別の集計
- 数日利用（使う場合は、日別に分けず通算で集計する方針）
- 終了後のデータの自動削除・案内

## MVP の完了条件

次の2つを満たしたら、MVP ができたとする（[0014](decisions/0014-mvp-done-criteria.md)）。

- SPEC の通りに実装され、GitHub Pages で公開されている
- SPEC が、ユーザージャーニーマップに合わせて見直されている

## 作り直しの進め方

- 定義し直した MVP を作り直す。サーバーは作らず、「API」は画面から呼ぶ `src/lib` の関数のこととする（[0022](decisions/0022-rebuild-mvp.md)）
- データの形式 → ロジック → 画面の順に、今のコードを層ごとに置き換える。Issue ごとの PR で、公開版が今までどおり動く状態を保つ（[0024](decisions/0024-rebuild-layer-by-layer.md)）
- データの形式は、今の形式で読めることを前提にせず考え直す（[0025](decisions/0025-rethink-data-formats.md)）
- Issue はマイルストーン「MVP 作り直し」にある
  - #15〜#20：データの形式
  - #21〜#32：ロジック
  - #33〜#43：画面
  - #44：PWA
  - #45：SPEC の通りか確かめて公開する

## MVP のあとで考えること

- 割引機能（[0011](decisions/0011-allow-negative-price.md)）
- 取消のしやすさ。レジを初めて使う人が取り消しやすいか、間違いが起こりにくいかを中心に考える（[0012](decisions/0012-keep-void-as-is.md)）
- 390px 幅でのレイアウト崩れ（#11）
- 開発者以外の出店者へのヒアリング（[ユーザージャーニーマップ](research/user-journey.md)の「ヒアリングで確かめること」）
- 上の「MVP でやらないこと」
