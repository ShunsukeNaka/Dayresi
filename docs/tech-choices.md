# 技術の選択

選んだ技術ごとに、メリットと、ほかの案を選ばなかった理由を書き足していく（[ADR 0029](decisions/0029-record-tech-choices.md)）。決めた経緯や理由（ユーザーが書くもの）は、各 Issue のコメントや ADR を見る。

## 商品と会計の ID：`crypto.randomUUID()`

- 決めた Issue：[#51](https://github.com/ShunsukeNaka/Dayresi/issues/51)（商品）、[#53](https://github.com/ShunsukeNaka/Dayresi/issues/53)（会計）
- 使う場所：商品を登録するときと、会計を確定するときに振る ID。会計の ID は画面に出さず、取消などで会計を指すのに使う

### メリット

- ブラウザの標準機能なので、npm パッケージを足さずに使える
- 122 ビットの乱数から作るので、実際には重ならない。登録した順番や時刻に左右されない
- 「一番大きい番号＋1」のように今ある商品を見て決める必要がないので、振る処理が商品の一覧に依存しない

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| 今の方式（`Date.now()` の 36 進数＋`Math.random()` 6 文字） | 同じミリ秒に 2 つ振ると、乱数 6 文字だけで区別することになる。標準の UUID のほうが重ならないことがはっきりしている |
| 1 からの連番 | 人が読めるが、商品 ID は画面に出さないので読めることに意味がない。振るたびに今ある商品の最大値を探す必要がある |
| 会計番号を会計の ID にする | 番号は重ならないので成り立つが、画面に出す番号と内部で指すための ID の役目が混ざる。商品と振り方をそろえたほうが分かりやすい |

### 注意

- 安全なページ（HTTPS か `localhost`）でしか使えない。GitHub Pages（HTTPS）と `npm run dev`・`npm run preview`（`localhost`）では動くが、ほかの端末から `http://192.168.…` で開くと動かない

## カートの持ち方：保存せず画面の state だけで持つ

- 決めた Issue：[#52](https://github.com/ShunsukeNaka/Dayresi/issues/52)
- 使う場所：レジ画面のカート（会計を確定する前の、商品ID → 数量）

### メリット

- カートは会計を確定する前の一時的な状態なので、保存しなくても失うのは打ちかけの会計だけで済む。打ち直せばよい
- 保存するデータが商品と会計だけになり、保存データの形式（#54）と読み書き（#64）が単純になる
- 保存しないので、全データ消去や商品の変更と、保存したカートとの食い違いを考えなくてよい

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| localStorage に保存して、再読み込みしても残す | 誤って再読み込みしても打ち直さずに済むが、保存するものが増え、保存データの形式と読み込みの確かめ方も増える。打ちかけの会計を失っても打ち直せば済むので、手間に見合わない |

## 会計の日時：ISO 8601 の文字列

- 決めた Issue：[#53](https://github.com/ShunsukeNaka/Dayresi/issues/53)
- 使う場所：会計の `at`（例 `2026-10-25T09:15:16.025Z`）

### メリット

- 保存データ（localStorage）を開いたときに、人が読んで日時が分かる
- 世界標準時で持つので、表示するときに PC の時刻に直せば、どの PC で開いてもずれない
- `Date#toISOString()` と `new Date(文字列)` で、そのまま書き出し・読み込みができる

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| ミリ秒の数値（`Date.now()`、例 `1792919716025`） | 比べたり並べたりするのは簡単だが、保存データを開いても人には読めない |

## 会計に商品名・価格・合計・おつりも保存する

- 決めた Issue：[#53](https://github.com/ShunsukeNaka/Dayresi/issues/53)
- 使う場所：会計の明細（`SaleItem` の `name` `price`）と会計（`Sale` の `total` `change`）

### メリット

- 履歴・集計・売上 CSV を、会計のデータだけで作れる。商品の一覧を探しにいかなくてよい
- 確定したときの金額をそのまま残すので、あとで計算の仕方を変えても過去の会計の金額が変わらない
- 将来、商品の編集を足しても、過去の会計の名前と価格が変わらない

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| 商品 ID と数量だけ持ち、商品名・価格・合計・おつりは使うたびに計算する | データは小さくなるが、使うたびに商品を探して計算する場所が増える。商品の一覧が変わると過去の会計も変わってしまう |

## 保存データの形式のバージョン：キー名で分ける（`dayresi:v2`）

- 決めた Issue：[#54](https://github.com/ShunsukeNaka/Dayresi/issues/54)
- 使う場所：商品と会計を保存する localStorage のキー

### メリット

- 形式を変えたらキー名を変えるだけで、古い形式と新しい形式が同じキーに混ざらない
- 読み込むときに、データの中身を見てバージョンで分ける処理がいらない
- 開発者ツールで localStorage を見たとき、キー名だけでどの形式か分かる

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| キーは `dayresi` のまま、データの中に `version` を持たせる | 読み込むたびに中身を開いてバージョンで分ける処理が要る。形式を変えたとき、古いデータを同じキーに上書きしてしまう |
| `dayresi:v1` のまま使う | 作り直す前の公開版のデータと形式が混ざる。今の形式との互換は前提にしない（ADR 0025） |

## 今の `dayresi:v1` のデータ：読まず、消さずに残す

- 決めた Issue：[#54](https://github.com/ShunsukeNaka/Dayresi/issues/54)
- 使う場所：作り直す前の公開版で保存されたデータ

### メリット

- 古い形式を読む処理を持たなくてよい
- 消さないので、あとで必要になっても、開発者ツールから取り出せる
- 何も書き換えないので、古いデータを壊すことがない

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| 読まずに消す | ブラウザに古いデータが残らないが、あとで必要になっても取り出せない。消す処理も要る |
| 読み込んで新しい形式に移す | 今まで使っていた人のデータを引き継げるが、古い形式を読む処理を持ち続けることになる。今の形式との互換は前提にしない（ADR 0025） |

## 売上 CSV の文字コードと改行：BOM 付き UTF-8・CRLF

- 決めた Issue：[#55](https://github.com/ShunsukeNaka/Dayresi/issues/55)
- 使う場所：設定画面の「売上CSVを保存」で書き出すファイル

### メリット

- 先頭に BOM を付けると、Excel がファイルを UTF-8 と判断するので、ダブルクリックで開いても日本語が文字化けしない
- UTF-8 なら、商品名にどんな文字（絵文字など）が入っていてもそのまま書ける。ブラウザの文字列をそのまま書き出せるので、変換の処理がいらない
- CRLF は CSV の標準（RFC 4180）の改行で、Windows の Excel でも古いソフトでも確実に行が分かれる

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| BOM なし UTF-8 | Excel でダブルクリックして開くと、Shift_JIS として読まれて日本語が文字化けする |
| Shift_JIS | Excel では開けるが、ブラウザには Shift_JIS に変換する標準の機能がないので、npm パッケージか変換表が要る。絵文字など Shift_JIS にない文字を書けない |
| LF | 今の Excel なら読めるが、古いソフトでは 1 行につながって見えることがある。CSV の標準でもない |

## 新しい版の反映：次にページを読み込んだときに新しい版になる

- 決めた Issue：[#75](https://github.com/ShunsukeNaka/Dayresi/issues/75)
- 使う場所：PWA の Service Worker（`vite.config.ts` の vite-plugin-pwa、`registerType: 'autoUpdate'`）

### メリット

- 開いているページは読み直さないので、会計の途中で画面が変わったり、カートが消えたりしない
- 次にページを読み込めば新しい版になるので、利用者が何も操作しなくても、いずれ新しい版に切り替わる
- 更新を知らせる画面を作らなくてよい（SPEC にない画面を足さずに済む）

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| 開いているページもすぐに読み直す | 新しい版がすぐ届くが、会計の途中でも読み直され、カートが消えることがある |
| 「更新」ボタンを出し、押したときに更新する | 利用者が選べるが、SPEC にない画面を足すことになる |

### 注意

- 一日のイベントの途中で新しい版を公開しても、ページを開いたままのレジは古い版のまま動く。再読み込みするまで新しい版にならない

## フォント：金額の Inter だけを同梱し、日本語は PC のフォントを使う

- 決めた Issue：[#112](https://github.com/ShunsukeNaka/Dayresi/issues/112)（[コメント](https://github.com/ShunsukeNaka/Dayresi/issues/112#issuecomment-6399659063)）
- 使う場所：金額・数量・テンキーの数字は Inter（npm の `@fontsource-variable/inter`、`src/main.tsx` で読み込む）。本文は PC にある日本語のフォント（Noto Sans JP・ヒラギノ・游ゴシック・メイリオの順に探す）。`src/index.css` の `--font-num` と `--font-ui`

### メリット

- アプリと一緒に配るので、通信がなくても金額がデザインどおりの数字で出る（Service Worker のキャッシュに入れる）
- キャッシュに入れるのは、数字・¥・−が入るラテン文字の分（約 48KB）だけなので、最初に開いたときの読み込みがほとんど重くならない
- 日本語のフォントは数 MB あるが、同梱しないので軽いままになる

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| Inter と Noto Sans JP を両方同梱する | どの PC でも同じ見た目になるが、日本語のフォントは数 MB あり、最初の読み込みとキャッシュが重くなる。npm パッケージも 2 つ増える |
| Google Fonts から読む | npm パッケージは増えないが、フォントをキャッシュする Service Worker の設定が要る。最初に開いたときに読めないと、PC のフォントで出る |
| 同梱しない（PC のフォントだけ） | npm パッケージは増えないが、金額の見た目がデザイン（Inter）と変わる |

### 注意

- 日本語の見た目は PC によって変わる（Windows は游ゴシックかメイリオ、Mac はヒラギノ）
- `@fontsource-variable/inter` はキリル文字・ギリシャ文字などの分のファイルもビルドに含むが、キャッシュには入れていない（`vite.config.ts` の `globPatterns`）。数字や ¥ では使われない

## 保存データの持ち方：レジの一覧を 1 つのキー（dayresi:v3）に入れる

- 決めた Issue：[#127](https://github.com/ShunsukeNaka/Dayresi/issues/127)
- 使う場所：`src/lib/storage.ts`（`loadStore`・`saveStore`）、`src/lib/registers.ts`、`src/types.ts` の `Store`・`Register`

### メリット

- レジの一覧と今のレジを 1 回の読み書きで扱えるので、途中で保存に失敗して、レジの一覧と中身が食い違うことがない
- 今までと同じ localStorage と JSON のままなので、npm パッケージも新しいブラウザの機能も要らない
- MVP の形式（dayresi:v2）は消さずに残し、v3 がないときだけ読んでマイレジに引き継ぐので、前の版に戻してもデータが残る

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| レジごとに別のキー（`dayresi:register:<id>`）に入れる | 1 つのレジだけを書き直せるが、レジの一覧と中身を別々に保存するので、途中で失敗すると食い違う。数日分のデータなら 1 つのキーでも十分小さい |
| IndexedDB に入れる | 大きなデータに向くが、読み書きが非同期になり、今の作り（起動時に同期で読む）を大きく変えることになる。データ量に対して大げさ |
| dayresi:v2 の形のまま、レジの情報を足す | キーを変えずに済むが、前の版が新しい形を読んで壊れたデータとして扱うおそれがある。形を変えたらキーのバージョンを上げる決まり（ADR 0025）にも合わない |

### 注意

- localStorage はブラウザごとに 5MB 前後まで。会計 1 件はおよそ 200〜300 バイトなので、1 万件でも数 MB に収まる

## QR コードを作るライブラリ：qrcode-generator

- 決めた Issue：[#129](https://github.com/ShunsukeNaka/Dayresi/issues/129)（[コメント](https://github.com/ShunsukeNaka/Dayresi/issues/129#issuecomment-6401190312)）
- 使う場所：`src/lib/qr.ts`（`qrModules`）。点の並びを `src/components/QrCode.tsx` で SVG に描く

### メリット

- 依存パッケージがなく、MIT ライセンスで、長く使われている
- 点の並び（`isDark`）を取り出せるので、SVG を自分で描いて A くっきりの見た目に合わせられる
- QR を作るのは端末の中だけなので、通信がなくても使える

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| uqr | 依存がなく小さく TypeScript 製だが、v0.1 台で使われた実績が少ない |
| qrcode | 一番よく使われているが、依存パッケージがあり大きめ。画像や CLI の機能は使わない |
| 自分で作る | QR の規格（誤り訂正など）を実装するのは手間が大きく、間違えやすい |

### 注意

- 読み取りはスマホ標準のカメラに任せるので、読み取るライブラリは入れていない
- スマホの画面からスマホのカメラで確実に読めるよう、大きさの上限をバージョン 25（117 × 117 の点）にした（`MAX_QR_VERSION`）。これを超えるデータは QR にせず、リンクで送ってもらう

## 端末のあいだで渡すデータ：URL の # 以降に、縮めた JSON を base64url で入れる

- 決めた Issue：[#129](https://github.com/ShunsukeNaka/Dayresi/issues/129)
- 使う場所：`src/lib/share.ts`（`encodeProductsShare`・`decodeShare`・`shareUrl`）

### メリット

- `#` 以降はサーバー（GitHub Pages）に送られないので、商品や会計のデータが外に出ない（ADR 0032）
- QR を標準のカメラで読んでも、リンクを LINE などで開いても、同じように Dayresi が開いて取り込める
- ブラウザ標準の `CompressionStream`（deflate-raw）で縮めるので、npm パッケージが要らない。商品 7 つのリンクは約 330 文字になった
- 先頭に版の番号を入れたので、形を変えても古い版のデータを見分けられる

### ほかの案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| JSON をそのまま入れる（縮めない） | 作りは簡単だが、商品 ID（UUID）や日本語の名前で長くなり、QR が大きくなる。会計を送るとさらに長くなる |
| URL の `?` 以降（クエリ）に入れる | GitHub Pages のサーバーに送られ、アクセスの記録に残るおそれがある |
| 独自のバイナリ形式に詰める | 一番短くできるが、作りと見直しが難しくなる |
| lz-string などの圧縮ライブラリ | 標準の機能で足りるので、npm パッケージを増やさない |

### 注意

- `CompressionStream` の deflate-raw は、Safari 16.4 以降・Chrome 103 以降で使える。それより古いブラウザでは、配る・取り込むができない
